# 第1項　LLMの出力を構造化する

## 概要

LLMは自然言語を入力とし、同じく自然言語を出力する仕組みです。近年の技術革新により、その能力と効果は広く証明されています。しかし、この「自然言語を入力して自然言語を出力する」性質は、LLMをソフトウェアに組み込む上で大きな障壁となります。一般的なプログラミング言語は、構造化されたデータを厳密に扱うことには長けていますが、非構造化テキストの曖昧さや多様性に柔軟に対応することには長けていません。もちろんプログラミング言語は自然言語を扱うことは可能ですが、構造化されたデータをやり取りするほうが得意と言えます。

本項では、LLMの出力をあらかじめ定義した構造に沿って受け取る「構造化出力」というプラクティスを紹介します。この手法を用いることで、システムはLLMの生成結果を安全かつ構造的に処理できるようになり、高い信頼性を持つシステム連携を実現します。

## 解決したい課題

LLMを組み込んだシステム開発で最も頻繁に直面する課題は、出力の不確実性です。LLMの応答は本質的に自然言語の文字列であるため、構造化データを前提とするプログラムとの間には設計上の根本的な隔たりがあります。

- プログラミングで頻繁に利用されるデータ構造

```python
from pydantic import BaseModel


# レビュー分析結果のデータクラス
class ReviewAnalysis(BaseModel):
    rating: int
    improvements: list[str]
```

- LLMの出力

```text
評価は4点で、改善要望は配送スピードです。
```

この不整合は、システムの安定稼働を妨げる様々な問題を引き起こします。

具体的な事例として、ECサイトの商品レビューから評価と改善点を抽出するシステムを考えてみましょう。LLMに「レビューから評価点と改善要望を抽出して」と指示した場合、「評価は5点満点中4点で、改善要望は配送スピードです」といった自然言語のテキストが返ってきます。このテキストから評価点「4」と改善要望「配送スピード」を確実に抜き出すには、複雑な文字列解析（パース）処理が必要です。「約4点」や「4〜5点」といった曖昧な表現が出力された場合、正確な数値の抽出はさらに困難になります。

もう一つの事例として、財務データ分析システムが挙げられます。LLMが「売上高は1,234,567円で、前年比約10%増でした」と出力したとします。プログラムがこの文字列を単純に処理しようとすると、カンマ区切りの数値を誤って「1」「234」「567」と分割してしまうリスクがあります。また、「約10%」という曖昧な表現から正確な数値を導き出すことも難しく、後続の計算処理に重大な誤りを引き起こしかねません。このような出力の不確実性はシステムの信頼性を著しく低下させ、特にビジネスクリティカルな領域でのLLM活用を妨げる大きな要因となっています。


## 解決策の提案

これらの課題を解決するため、LLMの出力を構造化するプラクティスを提案します。構造化出力は、LLMに対して事前に定義したデータ構造（スキーマ）に従って出力するよう明確に指示し、その構造に合致したJSONやデータクラス形式で応答を受け取る手法です。現代の主要なLLM APIは、OpenAIのStructured Output、Google GeminiのStructured Outputといった構造化出力をサポートする機能を標準で備えており、これらを活用することで型安全で信頼性の高いシステム連携が実現できます。

先の商品レビュー分析の例では、以下のようなJSONスキーマを定義します。

```json
{
  "rating": {
    "type": "number",
    "description": "1から5までの評価点",
    "minimum": 1,
    "maximum": 5
  },
  "improvements": {
    "type": "array",
    "description": "改善要望のリスト",
    "items": { "type": "string" }
  }
}
```

このスキーマをLLMに指示することで、`{"rating": 4, "improvements": ["配送スピード"]}` という構造化された出力を確実に得られます。PythonではPydanticライブラリを用いてこのスキーマをクラスとして定義し、受け取ったデータをバリデーションしながら型安全に扱うことができます。曖昧な表現は排除され、プログラムによる後続処理が劇的に簡素化されます。

財務データの例では、`{"revenue": 1234567, "currency": "JPY", "growth_rate": 0.1, "is_approximate": true}` という明確な構造で数値データを取得するスキーマを定義します。これにより、カンマの問題や曖昧な表現を排除し、正確なデータ処理が可能になります。さらに、スキーマに従わない応答を検知するバリデーション機能を組み込むことで、適切な例外処理やリトライを実行し、システムの堅牢性を大幅に向上させることが可能です。

## 適応するユースケース

LLMの出力を構造化するプラクティスは、特にデータの正確性と一貫性が求められるシステムにおいて絶大な効果を発揮します。

医療診断支援システムは、その典型的なユースケースです。患者が入力した症状のテキストから、構造化された診断候補や関連情報を抽出する場合を考えます。`{"symptoms": ["頭痛", "発熱"], "severity": "中度", "urgency_level": 2, "recommended_departments": ["内科", "総合診療科"]}` という構造化出力が得られれば、医療従事者は標準化されたフォーマットで情報を迅速に把握し、正確な判断を下す助けとなります。非構造化テキストのままでは見落とされがちな重要情報も、構造化によって確実に捉えることができ、最終的に患者の安全性向上に貢献します。

金融取引システムにおける市場分析レポートの自動生成も、このプラクティスが活きる重要なユースケースです。膨大なニュース記事や市場データから、`{"market_sentiment": "bullish", "confidence_score": 0.75, "key_factors": ["中央銀行の金利政策", "主要企業の業績発表"], "risk_level": "medium"}` といった構造化データをリアルタイムで生成します。この構造化データは、自動売買システムのトリガーとして直接利用したり、人間のトレーダーへの意思決定支援情報として提供したりできます。さらに、構造化された出力はそのまま監査証跡（ログ）としても活用でき、規制要件への対応も容易になります。

## 導入のポイント

このプラクティスを効果的に導入するためには、いくつかの重要なポイントがあります。

第一に、出力スキーマは必要最小限のフィールドから始め、段階的に拡張するアプローチが重要です。初期段階では3〜5個の必須フィールドに絞って設計し、システムの運用を通じて真に必要性が確認されたフィールドを徐々に追加していきます。これにより、過度に複雑なスキーマが保守性を低下させる事態を防ぎ、開発初期の機動性を確保できます。

第二に、Python環境ではPydanticを活用したスキーマ定義とバリデーションを徹底することが推奨されます。`from pydantic import BaseModel, Field` を用いてスキーマをクラスとして定義し、`rating: int = Field(description="1から5までの評価点", ge=1, le=5)` のように、型情報に加えて制約条件や説明を明示的に記述します。これにより、開発時点での整合性チェックが容易になるだけでなく、実行時の自動バリデーションも実現できます。

第三に、構造化出力機能を公式にサポートするモデルを選択することです。OpenAIのGPT-4シリーズやAnthropicのClaude 3シリーズといった最新モデルは、これらの機能を高い精度でサポートしており、安定した運用が期待できます。その上で、構造化出力が失敗した場合に備えたフォールバック戦略（例：より単純なプロンプトでリトライする、エラーを記録して手動対応を依頼する）を必ず実装し、システム全体の可用性を確保することが不可欠です。

## 注意点とトレードオフ

構造化出力を採用する際には、いくつかの注意点とトレードオフを慎重に考慮する必要があります。

最も重要なのは、スキーマの厳密性とLLMの柔軟性のバランスです。過度に厳密なスキーマは、LLMの創造性を制限し、予期せぬ有益な情報を取りこぼす可能性があります。例えば、商品レビュー分析で固定カテゴリのフィールドのみを定義すると、ユーザーが記述した新しい観点からの貴重なフィードバックを見逃すかもしれません。このトレードオフに対しては、必須フィールドと任意フィールドを適切に組み合わせたり、`"additional_info": {"type": "object"}` のように未知のキーを許容する拡張可能な構造をスキーマに含めたりすることで対処できます。

次に、コストとパフォーマンスへの影響も無視できません。構造化出力のためのスキーマ定義や指示はプロンプトを長くするため、APIリクエストあたりのトークン数が通常のプロンプトに比べて増加する傾向があります。これによりAPIコストが上昇し、応答時間もわずかに長くなる可能性があります。大規模なシステムでこのプラクティスを全面的に採用する際は、コストへの影響を事前に見積もり、キャッシング戦略やリクエストのバッチ処理といった最適化手法を検討する必要があります。

最後に、モデルのバージョンアップに伴う互換性の問題です。LLMは継続的にアップデートされており、新しいバージョンでは構造化出力の精度が向上する一方、稀に挙動が微妙に変化することがあります。例えば、GPT-3.5からGPT-4への移行時に、同じスキーマでも出力されるJSONのキーの順序が変わったり、微妙なフォーマットが変更されたりして、既存の解析ロジックが動作しなくなる事例も報告されています。このリスクに備え、モデルバージョンごとにテストスイートを整備し、段階的な移行戦略を採用することで、サービスの継続性を保証することが重要です。

## まとめ

本項で解説した「LLMの出力を構造化する」プラクティスは、生成AIをエンタープライズ品質のシステムに統合する上で不可欠な手法です。このアプローチにより、自然言語が持つ本質的な曖昧さを排除し、型安全で予測可能なシステム連携を実現できます。医療、金融、ECといった高い信頼性が要求される領域においても、適切なスキーマ設計と堅牢な例外処理を組み合わせることで、LLMを安心して活用するための道筋が拓かれます。
