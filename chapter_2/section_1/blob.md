# 第1項　LLMの出力を構造化する

## 概要

LLMは自然言語を入力とし、同じく自然言語を出力する仕組みです。近年の技術革新により、その能力と効果は広く証明されています。しかし、この「自然言語を入力して自然言語を出力する」性質は、LLMをソフトウェアに組み込む上で大きな障壁となります。というのも、一般的なプログラミング言語は構造化されたデータを扱うことには長けていますが、非構造化テキストの曖昧さや多様性に柔軟に対応するようには作られていません。もちろんプログラミング言語で自然言語を扱うことは可能ですが、構造化されたデータをやり取りするほうが得意と言えるでしょう。

本項では、LLMの出力をあらかじめ定義した構造に沿って受け取る「構造化出力」というプラクティスを紹介します。この手法を用いることで、システムはLLMの生成結果を安全かつ構造的に処理できるようになり、システム連携の信頼性や安定性を向上します。

## 解決したい課題

LLMを組み込んだシステム開発で頻繁に直面する課題のひとつに、出力の不確実性が挙げられます。LLMの応答は本質的に自然言語の文字列であるため、構造化データを前提とするプログラムとの間には設計上の根本的な隔たりがあります。

- プログラミングで頻繁に利用されるデータ構造の例

```python
from pydantic import BaseModel


# レビュー分析結果のデータクラス
class ReviewAnalysis(BaseModel):
    rating: int
    improvements: list[str]
```

- LLMの出力例

```text
評価は4点で、改善要望は配送スピードです。
```

この不整合は、システムの安定稼働を妨げる様々な問題を引き起こします。

具体的な例として、ECサイトの商品レビューから評価と改善点を抽出するシステムを考えてみましょう。LLMに「レビューから評価点と改善要望を抽出して」と指示した場合、「評価は5点満点中4点で、改善要望は配送スピードです」といった自然言語のテキストが返ってきます。このテキストから評価点「4」と改善要望「配送スピード」を正確に抜き出すためには、複雑な文字列解析（パース）や正規表現処理が必要になります。LLMから「約4点」や「4〜5点」といった曖昧な表現が出力された場合、正確な数値の抽出はさらに困難になります。

もう一つの事例として、財務データ分析システムを考えてみます。LLMが「売上高は1,234,567円で、前年比約10%増でした」と出力したとします。プログラムがこの文字列を単純に処理しようとすると、カンマ区切りの数値を誤って「1」「234」「567」と分割してしまうかもしれません。また、「約10%増」という曖昧な表現から正確な数値を導き出すことも難しく、後続の計算処理に誤りを引き起こしかねません。このような出力の不確実性はシステムの信頼性を低下させ、特にビジネスクリティカルな領域でソフトウェアを組み合わせたLLM活用を妨げる要因となります。


## 解決策の提案

これらの課題を解決するため、LLMの出力を構造化するプラクティスを提案します。構造化出力では、LLMに対して事前に定義したデータ構造（スキーマ）に従って出力するよう明確に指示し、その構造に合致したJSONやデータクラス形式で応答を受け取ることができます。主要なLLM APIであるOpenAI、Google Gemini、Anthropic Claudeはいずれも構造化出力をサポートしており、これらを活用することで型安全で信頼性の高いシステム連携が実現できます。

先の商品レビュー分析の例では、以下のようなJSONスキーマを定義します。

```json
{
  "rating": {
    "type": "number",
    "description": "1から5までの評価点",
    "minimum": 1,
    "maximum": 5
  },
  "improvements": {
    "type": "array",
    "description": "改善要望のリスト",
    "items": { "type": "string" }
  }
}
```

このスキーマをLLMに指示することで、`{"rating": 4, "improvements": ["配送スピード"]}` という構造化された出力を確実に得られます。PythonではPydanticライブラリを用いてこのスキーマをクラスとして定義し、受け取ったデータをバリデーションしながら型安全に扱うことができます。曖昧な表現は排除され、プログラムによる後続処理が大幅に簡素化されます。

財務データの例では、`{"revenue": 1234567, "currency": "JPY", "growth_rate": 0.1, "is_approximate": true}` という明確な構造で数値データを取得するスキーマを定義します。これにより、カンマの問題や曖昧な表現を排除し、正確なデータ処理が可能になります。さらに、スキーマに従わない応答を検知するバリデーション機能を組み込むことで、適切な例外処理やリトライを実行し、システムの堅牢性を大幅に向上させることが可能です。

## 適用するユースケース

LLMの出力を構造化するプラクティスは、特にデータの正確性と一貫性が求められるシステムにおいて大きな効果を発揮します。

医療診断支援システムは、その典型的なユースケースです。患者が入力した症状のテキストから、構造化された診断候補や関連情報を抽出するケースを考えます。`{"symptoms": ["頭痛", "発熱"], "severity": "中度", "urgency_level": 2, "recommended_departments": ["内科", "総合診療科"]}` という構造化出力が得られれば、医療従事者は標準化されたフォーマットで情報を迅速に把握し、正確な判断を下す助けとなるでしょう。非構造化テキストのままでは見落とされがちな重要情報も、構造化によって確実に捉えることができ、最終的に患者の安全性向上に貢献します。

金融取引システムにおける市場分析レポートの自動生成も、このプラクティスが活きる重要なユースケースです。膨大なニュース記事や市場データから、`{"market_sentiment": "強気", "confidence_score": 0.75, "key_factors": ["中央銀行の金利政策", "主要企業の業績発表"], "risk_level": "medium"}` といった構造化データを生成します。この構造化データは、自動売買システムのトリガーとして直接利用したり、人間のトレーダーへの意思決定支援情報として提供したりできます。さらに、構造化された出力はそのまま監査証跡（ログ）としても活用でき、規制要件への対応も容易になるでしょう。

## 導入のポイント

このプラクティスを効果的に導入するためには、いくつかの重要なポイントがあります。

第一に、出力スキーマは必要最小限のフィールドから始め、段階的に拡張するアプローチが重要です。初期段階では3〜5個の必須フィールドに絞って設計し、システムの運用を通じて真に必要性が確認されたフィールドを徐々に追加していきます。これにより、過度に複雑なスキーマが保守性を低下させる事態を防ぎ、開発初期の機動性を確保できます。

第二に、Python環境ではPydanticを活用したスキーマ定義とバリデーションを徹底することを推奨します。`from pydantic import BaseModel, Field` を用いてスキーマをクラスとして定義し、`rating: int = Field(description="1から5までの評価点", ge=1, le=5)` のように、型情報に加えて制約条件や説明を明示的に記述します。これにより、開発時点での整合性チェックが容易になるだけでなく、実行時の自動バリデーションも実現できます。その上で、構造化出力が失敗した場合に備えたフォールバック戦略（例：より単純なプロンプトでリトライする、エラーを記録して手動対応を依頼する）を必ず実装し、システム全体の可用性を確保することが不可欠です。

第三に、構造化出力機能を公式にサポートするモデルを選択することです。すべてのLLMモデルやLLM APIが構造化出力をサポートしているとは限りません。各LLMプロバイダーの公式ドキュメントを確認し、構造化出力をサポートしているモデルを選択することを忘れてはなりません。

## サンプルコード
以下に構造化出力を活用したサンプルコードとともに、実装方法を解説します。

### 1. データモデルの定義

まず、Pydanticを使用して構造化出力のスキーマを定義します。このモデルは、フィクションのキャラクター情報を表現するものです。

```python
from enum import StrEnum
from pydantic import BaseModel, ConfigDict, Field


class Gender(StrEnum):
    FEMALE = "female"
    MALE = "male"


class CharacterPersonality(BaseModel):
    model_config = ConfigDict(
        validate_assignment=True,
        frozen=True,
        extra="ignore",
    )

    short_personality: str = Field(..., description="A short description of the character's personality.")
    description: str = Field(..., description="A description of the character's personality traits and behaviors.")


class CharacterResponse(BaseModel):
    model_config = ConfigDict(
        validate_assignment=True,
        frozen=True,
        extra="ignore",
    )

    first_name: str = Field(..., description="The first name of the character.")
    last_name: str = Field(..., description="The last name of the character.")
    gender: Gender = Field(Gender.MALE, description="The gender of the character.")
    age: int = Field(..., description="The age of the character.", ge=0, le=100)
    personalities: list[CharacterPersonality] = Field(
        ..., description="The three most important personality traits of the character."
    )
```

このスキーマ定義により、以下のような型安全性と検証機能が実現されます：

- `Gender`は列挙型で定義され、"female"または"male"のいずれかの値のみを受け付けます
- `age`フィールドには`ge=0, le=100`により0から100の範囲制約が設定されています
- `frozen=True`により、データの不変性が保証されます
- `validate_assignment=True`で、代入時の自動検証が有効化されます

### 2. OpenAIでの構造化出力の実装

OpenAI APIの`responses.parse()`メソッドを使用して構造化出力を取得します。

```python
from openai import AsyncOpenAI
from src.model.model import CharacterResponse

openai_client = AsyncOpenAI(api_key=your_api_key)

async def request_openai(model: str) -> CharacterResponse:
    prompt = [
        {
            "role": "system",
            "content": """あなたは創造的なキャラクタージェネレーターです。
以下の構造に厳密に従ったJSONオブジェクトで応答する必要があります。
すべてのフィールドを含め、性別は「female」または「male」、
年齢は0から100の間、正確に3つの性格特性を提供してください。"""
        },
        {
            "role": "user",
            "content": "ユニークで興味深いフィクションのキャラクターを、詳細な性格と共に生成してください。"
        }
    ]

    result = await openai_client.responses.parse(
        model=model,
        input=prompt,
        text_format=CharacterResponse,  # Pydanticモデルを直接指定
    )
    return result.output_parsed
```

OpenAIの実装では、`text_format`パラメータにPydanticモデルを渡すことで、APIが自動的にスキーマに従った出力を生成し、返り値は既にPydanticオブジェクトとしてパースされた状態で取得できます。

### 3. 実行例と出力結果

上記のいずれかの実装を実行すると、以下のような構造化されたJSONデータが得られます：

```json
{
    "first_name": "蒼",
    "last_name": "雨宮",
    "gender": "male",
    "age": 28,
    "personalities": [
        {
            "short_personality": "内向的な思索家",
            "description": "常に深く物事を考え、静かな場所を好む。表面的な会話よりも、哲学的な議論に心を開く。"
        },
        {
            "short_personality": "完璧主義者",
            "description": "すべてのタスクに最高の基準を求め、細部にこだわる。しばしば自分自身に対して厳しすぎることがある。"
        },
        {
            "short_personality": "忠実な友人",
            "description": "一度信頼関係を築くと、どんな困難な状況でも友人を支える。約束を何よりも大切にする。"
        }
    ]
}
```

このデータは、Pydanticモデルによって以下のように自動検証されます：

- `age`が0から100の範囲内にあることを確認
- `gender`が"male"または"female"のいずれかであることを確認
- `personalities`が正確に3つの要素を持つリストであることを確認
- すべての必須フィールドが存在することを確認

型検証に失敗した場合、Pydanticは自動的に`ValidationError`を発生させ、具体的なエラー内容を示します。これにより、不正なデータが後続の処理に渡されることを防ぎ、システムの堅牢性が大幅に向上します。

### 4. プロバイダー間の実装の違い

3つのプロバイダーの構造化出力実装には、それぞれ特徴があります：

- **OpenAI**: `text_format`パラメータでPydanticモデルを直接指定。シンプルで直感的なAPI設計。
- **Gemini**: `response_schema`と`response_mime_type`を組み合わせて使用。system_instructionとcontentsを分離して指定する設計。
- **Anthropic**: ベータ機能として提供されており、`betas`パラメータで機能を有効化する必要がある。`output_format`でスキーマを指定。

いずれのプロバイダーも、最終的にはPydanticモデルに基づいた型安全な構造化出力を実現できます。プロバイダーの選択は、コスト、レスポンス速度、モデルの性能などの要件に応じて行うことができます。

## 注意点とトレードオフ

構造化出力を採用する際には、いくつかの注意点とトレードオフを慎重に考慮する必要があります。

最も重要なのは、スキーマの厳密性とLLMの柔軟性のバランスです。過度に厳密なスキーマは、LLMの創造性を制限し、予期せぬ有益な情報を取りこぼす可能性があります。例えば、商品レビュー分析で固定カテゴリのフィールドのみを定義すると、ユーザーが記述した新しい観点からの貴重なフィードバックを見逃すかもしれません。このトレードオフに対しては、必須フィールドと任意フィールドを適切に組み合わせたり、自然言語で自由記述するフィールドを用意する拡張可能性を含めることで対処できます。

次に、コストとパフォーマンスへの影響も無視できません。構造化出力のためのスキーマ定義や指示はプロンプトを長くするため、APIリクエストあたりのトークン数が通常のプロンプトに比べて増加する傾向があります。これによりAPIコストが上昇し、応答時間もわずかに長くなる可能性があります。大規模なシステムでこのプラクティスを全面的に採用する際は、コストへの影響を事前に見積もり、キャッシング戦略等を検討する必要があります。

## まとめ

本項で解説した「LLMの出力を構造化する」プラクティスは、生成AIを安定してソフトウェアに統合する上で不可欠な手法です。このアプローチにより、自然言語が持つ本質的な曖昧さを抑制し、型安全で予測可能なシステム連携を実現できます。医療、金融、ECといった高い信頼性が要求される領域においても、適切なスキーマ設計と堅牢な例外処理を組み合わせることで、LLMを安心して活用するための道筋が拓かれるでしょう。
