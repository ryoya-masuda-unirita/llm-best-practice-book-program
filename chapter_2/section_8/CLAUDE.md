# Section 7: Evaluating LLMs with LLMs (LLM-as-a-Judge Implementation)

## Project Overview

This project demonstrates a sample implementation of **LLM-as-a-Judge**, a design pattern that leverages LLMs as evaluators. It achieves automated quality management and improved efficiency by having one LLM automatically evaluate the character information generated by another LLM.

The implementation supports both OpenAI GPT-5.4-mini and Google Gemini 2.5 Flash, with particular emphasis on **cross-provider evaluation** (using different providers for generation and evaluation). This approach mitigates model-specific biases and enables more objective assessments.

## Background: Problems to Solve

In systems development incorporating LLMs, managing output quality is a critical challenge. Issues stemming from manual evaluation processes particularly impact both development velocity and quality.

Consider a customer support system that automatically responds to inquiries. Manually reviewing thousands of daily response logs—verifying factual accuracy and understanding of customer intent—is impractical. Relying on sampling surveys risks missing problematic responses, potentially leading to decreased customer satisfaction.

Prompt improvement work also faces evaluation challenges. When comparing multiple prompt variations, evaluators often make subjective judgments like "this expression feels more natural" or "the previous version was more polite." Such person-dependent evaluations lack consistency, making it difficult to objectively determine which prompts are truly superior.

## Implementation Solution

This project implements an approach that leverages LLMs themselves as evaluators. Specifically, responses generated by the character generation LLM are input to a separate LLM with an evaluation-specific prompt to produce scoring and feedback.

### Implementation Features

1. **Automated Evaluation with Three Criteria**
   - **Accuracy**: Whether the response is accurate and factually correct for the question
   - **Comprehensiveness**: Whether the response contains sufficient necessary information
   - **Clarity**: Whether the response is easy to understand and appropriately expressed

2. **Five-Point Scoring Scale**
   - 1 point: Completely inappropriate
   - 2 points: Poor
   - 3 points: Acceptable (default quality threshold)
   - 4 points: Good
   - 5 points: Perfect

3. **Structured Evaluation Results**
   - Score and reasoning for each criterion
   - Overall score (average)
   - Evaluation summary
   - All output in JSON format for easy downstream processing

4. **Cross-Provider Evaluation**
   - Support for using different LLM providers for generation and evaluation
   - Mitigates model-specific biases
   - Enables more objective assessment

## Project Architecture

### Core Components

#### 1. Data Model Layer (`src/model/`)

**Character Models** (`model.py`):
- `CharacterRequest`: Character generation request
- `CharacterResponse`: Generated character information
- `CharacterPersonality`: Personality trait details

**Evaluation Models** (`llm_as_a_judge_model.py`):
- `EvaluationScore`: 1-5 evaluation score (IntEnum)
- `EvaluationCriterion`: Individual criterion evaluation result
- `JudgeRequest`: Evaluation request (question, response, context)
- `JudgeResponse`: Evaluation result (evaluations, overall_score, summary)

#### 2. Prompt Generation Layer (`src/prompt/`)

**Character Generation Prompts** (`prompt.py`):
- Prompt generation with embedded schema information
- Dynamic prompt construction based on requests

**Evaluation Prompts** (`llm_as_a_judge_prompt.py`):
- `make_judge_prompt()`: Standard three-criterion evaluation prompt
- `make_custom_judge_prompt()`: Custom evaluation criteria support
- Explicit definition of evaluation criteria and scoring guide

#### 3. Service Layer (`src/service/`)

**LLM Request Processing** (`request_llm.py`):
- `request_openai()`: Character generation with OpenAI
- `request_gemini()`: Character generation with Gemini
- `request_with_judge()`: Integrated workflow for generation and evaluation

**LLM-as-a-Judge Evaluation Service** (`llm_as_a_judge.py`):
- `judge_with_openai()`: Evaluation using OpenAI
- `judge_with_gemini()`: Evaluation using Gemini
- Both functions use temperature=0.0 to ensure evaluation consistency

#### 4. CLI Layer (`src/main.py`)

Command-line interface providing:
- Character attribute specification (gender, age, additional instructions)
- Selection of generation LLM provider/model
- **Selection of evaluation LLM provider/model (optional)**
- Automatic evaluation execution and result saving
- Quality threshold checking and warnings

## Implementation Details

### Integrated Workflow

The `request_with_judge()` function completes both generation and evaluation in a single function:

```python
async def request_with_judge(
    prompt: list,
    model: OpenAIModel | GeminiModel,
    provider: str,
    judge_model: OpenAIModel | GeminiModel | None = None,
    judge_provider: str | None = None,
) -> tuple[CharacterResponse, JudgeResponse]:
    # Step 1: Character generation
    if provider == "openai":
        character_response = await request_openai(prompt, model)
    elif provider == "gemini":
        character_response = await request_gemini(prompt, model)

    # Step 2: Create evaluation request
    judge_request = JudgeRequest(
        question=user_prompt,
        response=character_response.model_dump_json(indent=2),
        context=None
    )

    # Step 3: Execute evaluation
    if judge_provider == "openai":
        judge_response = await judge_with_openai(judge_request, judge_model)
    elif judge_provider == "gemini":
        judge_response = await judge_with_gemini(judge_request, judge_model)

    return character_response, judge_response
```

### Ensuring Evaluation Consistency

The evaluation service ensures consistency through the following approaches:

1. **Low Temperature Parameter**: Deterministic evaluation with `temperature=0.0`
2. **Structured Output**: Strict type validation with Pydantic models
3. **Explicit Evaluation Criteria**: Specific criteria included in prompts
4. **Cross-Provider Support**: Cross-validation with different models

## Usage

### Basic Usage (Same Provider)

```bash
# Generate with Gemini, evaluate with Gemini
python -m src.main -g female -a 25 -lp gemini -m gemini-2.5-flash
```

### Cross-Provider Evaluation (Recommended)

```bash
# Generate with Gemini, evaluate with OpenAI
python -m src.main \
  -g female -a 25 \
  -lp gemini -m gemini-2.5-flash \
  -jp openai -jm gpt-5.4-mini
```

### Output Files

Execution generates two JSON files:

1. **Character File**: `{generation_provider}_character_{uuid}.json`
2. **Evaluation File**: `{evaluation_provider}_judge_{uuid}.json`

This LLM-as-a-Judge implementation can be applied to the following use cases:

Automatically evaluate all generation results and track score trends to detect system quality degradation early.

### 4. Automated Filtering
Automatically detect generation results below the quality threshold (default 3.0/5.0) and route them for regeneration or human review.

## Implementation Best Practices

### Clear Definition of Evaluation Criteria

The implementation clearly defines three evaluation criteria:

```python
[Evaluation Criteria]
1. Accuracy: Whether the response is accurate and factually correct
   - Faithfulness to reference information when provided
   - Absence of incorrect information or hallucinations

2. Comprehensiveness: Whether sufficient necessary information is included
   - Direct response to user questions
   - No missing critical information

3. Clarity: Whether the response is easy to understand and appropriately expressed
   - No unnecessary technical jargon
   - Readable sentence structure
```

### Custom Evaluation Criteria

Using the programmatic API, you can define domain-specific evaluation criteria:

```python
custom_criteria = [
    {
        "name": "empathy",
        "description": "Ability to express understanding of customer concerns and frustrations"
    },
    {
        "name": "solution-oriented",
        "description": "Ability to present concrete solutions and next steps"
    }
]

prompt = make_custom_judge_prompt(request, custom_criteria)
```

### Improving Evaluation Stability

The implementation ensures evaluation stability through the following methods:

1. **Low Temperature Setting**: Consistent evaluation with `temperature=0.0`
2. **Cross-Provider Evaluation**: Cross-validation with different models
3. **Structured Output**: Strict type validation with Pydantic models
4. **Quality Threshold Check**: Automatic determination with `is_passing(threshold)` method

## Considerations and Trade-offs

### Limitations

1. **Judge LLM Limitations**: The evaluating LLM is not perfect and may contain biases or errors
2. **Increased Costs**: Additional API calls for evaluation increase costs
3. **Latency**: Evaluation processing increases overall processing time
4. **Evaluation Criteria Design**: Poorly designed criteria can lead to large-scale automation of incorrect judgments

### Trade-offs

**Automation vs. Precision**:
- Faster than human evaluation but inferior in understanding nuances
- Solution: Hybrid approach where humans review only low-scoring results

**Consistency vs. Bias**:
- Evaluation criteria are consistent, but model-specific biases exist
- Solution: Cross-validation through cross-provider evaluation

**Coverage vs. Cost**:
- Can evaluate all outputs, but API costs increase
- Solution: Sampling evaluation or asynchronous batch processing
